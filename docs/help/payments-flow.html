The payment flow, end to end

A merchant shows a QR; a customer scans it and pays. Behind that simple act is a precise contract — the futurechain:pay URI — and a shared SDK that all three payment apps rely on. This page traces a payment from the merchant's keypad to the local receipt, and is honest about what is built and what still waits on the FutureChain core.

1What the payment flow is

The payment flow is the rail that connects three of ANTON's phone apps. ANTON Business is the merchant side — it builds a payment request. ANTON Pay and the wallet inside ANTON Comm are the customer side — they read that request and act on it.

The thing in the middle is not a server. It is a data format — the futurechain:pay URI — usually carried as a QR code on a screen. Business encodes it; Pay and Comm decode it. Because the contract is just data, no payment server has to be online for the apps to agree on what is being paid.

⟪

Business builds

The merchant enters an amount or a cart; the app encodes a futurechain:pay URI and shows it as a QR.

☀

Pay / Comm read

The customer scans, the URI is decoded and validated, and a review screen appears.

⛓

Settled bilaterally

The actual on-chain transfer happens off-app, merchant ↔ Safello. The apps keep local records.

2How to think about it

🧭The mental model

Think of the futurechain:pay URI as a written invoice. The merchant fills it in completely — who to pay, how much, what for, who they legally are, when it expires — and the customer's app simply reads it back. The customer's app never invents a figure. If a number is wrong on the review screen, the invoice was wrong; the app is a faithful reader, not an author.

Three ideas hold the rest of this page together:

  • The URI is the whole agreement. Everything the customer sees — amount, merchant, purpose, VAT, expiry, the merchant's ISO 20022 identity — was placed in the URI by the merchant. There is no second channel.
  • The SDK is shared, and partly stubbed. All three apps build on one @futurechain/sdk package. Some of it is solid and tested; some of it deliberately throws until the FutureChain Rust core is vendored. This page names which is which — and so does Build status.
  • Settlement is not the apps' job. The apps agree on the payment and record it. Moving the money is bilateral between the merchant and Safello, off-app. The apps are honest ledgers, not a clearing house.
⚠Drafts today, signatures later

When you confirm a payment, the apps assemble a full ISO 20022 PACS.008 draft and show it to you — but that draft is not yet cryptographically signed. Real signing is blocked on the FutureChain Rust core being vendored. The apps are built so the draft populates and displays now, and signing simply switches on when the SDK unstubs. See Build status.

3The futurechain:pay URI — the contract

The URI is encoded by ADR-004 v1. Here is what each field carries.

FieldCarries
toThe merchant's FutureChain receive address — where the payment is destined.
amountThe amount in micro-FTC (integer) — no floating point on the wire.
refThe ADR-004 v1 reference: an 8-char merchant id (M:), a 12-char order id (O:), the purpose, and optional item count / VAT / discount.
cn / cc / cct / cst / cpcThe merchant's ISO 20022 creditor party — name, country, and the address components — so the payer can build a complete PACS.008 record.
expAn expiry timestamp — Business sets it ~15 minutes ahead. An expired URI is rejected on scan.
vFormat version — 1.

The ref purpose is one of RETAIL / RESTAURANT / EVENT / SERVICE / REFUND. On the payer side, when the PACS.008 draft is assembled, that purpose is mapped to an ISO 20022 external purpose code: RETAIL→GDDS, RESTAURANT/SERVICE→SCVE, EVENT→OTHR, REFUND→REFUND.

💡Why amounts are integers

The amount field is micro-FTC as a whole number — 12.50 FTC travels as 12500000. Integer arithmetic has no rounding surprises, so the figure the merchant typed is bit-for-bit the figure the customer confirms. The currency estimate a payer app shows (e.g. "≈ 138 SEK") is a live convenience only; the FTC amount is what is actually paid.

How it works ADR-004 & the reference module +

The encoding rules are defined by ADR-004 (the architecture decision record under anton-business/docs/adr/). There are two reference versions: v1 is merchant-bearing — it carries the full creditor party so a payer can assemble a PACS.008 — and v2 is an operational, leaner form.

Encoding and decoding are handled by the SDK's reference module (anton-business/packages/futurechain-sdk/src/reference/). A key design property: reference.decode() never throws. It returns a discriminated union — success with the parsed fields, or a typed failure — so a malformed or hostile QR is a handled value, not a crash. This is the BUILT part of the SDK, with a deterministic encode/decode round-trip covered by reference.test.ts.

4The FutureChain SDK, module by module

All three payment apps depend on one workspace package, @futurechain/sdk. It is partially implemented — and deliberately honest about it. Each stubbed function throws a NotImplementedError whose message names the artifact it is blocked on, so the failure is self-diagnosing.

ModulePurposeStatus
referenceADR-004 remittance encoding — v1 (merchant-bearing) & v2 (operational). Never throws; returns a discriminated union.BUILT
taxJurisdiction-aware crypto-asset tax engine — cost basis, holding-period relief, loss offset, K4/CSV reports.IN PROGRESS
walletsecp256k1 keys, mnemonics, signing. Address derivation works; create / sign / verify stubbed.PARTIAL

rpcRPC envelope between app and backend.STUB
⚠The critical-path blocker

The pacs008 builder throws NotImplementedError — it is blocked on the FutureChain Rust core file iso20022_pacs008.rs being vendored, so the canonical byte form can be matched exactly. Until then, Pay and Comm assemble PACS.008 drafts as plain object literals: they are fully populated and shown to the user, but not signed. Signed payment records and real settlement all wait downstream of this one artifact.

How it works Building a PACS.008 draft today +

On the payer side (ANTON Pay), the service pacs008-draft.ts assembles an ISO 20022 PACS.008 draft when the user confirms. The debtor party is the payer's saved identity — or a bare wallet address if identity entry was skipped — and the creditor party is read straight from the scanned URI's cn/cc/cct/cst/cpc fields. The ADR-004 purpose is mapped to its ISO external purpose code at this point.

The draft is stored on the local payment record. It is a plain object literal — deliberately not run through the stubbed @futurechain/sdk/pacs008 builder, which would throw. When the SDK unstubs, the same draft data flows into the real builder for canonical serialisation, hashing and signing — no change to what the apps collect today.

  1. The merchant builds the request

    In ANTON Business, the merchant either taps a flat amount on the keypad (Simple mode) or builds a cart with per-item VAT (Extended mode). The app encodes a futurechain:pay URI carrying the receive address, the amount in micro-FTC, the ADR-004 v1 ref, the merchant's ISO 20022 creditor party and a ~15-minute expiry.

  2. The merchant shows the QR

    The URI is rendered as a QR on the merchant's phone screen.

  3. The customer scans & the URI is decoded

    Pay or Comm reads the QR and calls reference.decode(), which validates the scheme, version and expiry. An expired or malformed code is rejected with a clear message — never a crash.

  4. The customer reads the review screen

    The decoded payment is shown in plain language: FTC amount and an estimated local-currency value, the merchant, the purpose, VAT, a live expiry countdown, and an expandable ISO 20022 detail panel.

  5. The fraud engine scores it

    The on-device 9-rule fraud engine compares the payment to the customer's own pattern and surfaces any signals. It is always advisory — see ANTON Pay §5.

  6. The customer confirms

    On confirm, Pay/Comm record the payment locally and assemble the PACS.008 draft from the saved identity and the scanned creditor. Business records a matching kvitto in its gap-free ledger. Settlement then happens bilaterally, off-app, between the merchant and Safello.

📌Example — an itemised café sale

A café builds an Extended-mode cart: two coffees and a sandwich, 25% VAT, 11.20 FTC total. Business encodes a futurechain:pay URI — amount=11200000, ref with merchant id, order id and purpose RESTAURANT, the café's creditor party, exp 15 minutes out — and shows the QR. The customer's Pay app decodes it, shows 11.20 FTC · Café Lindgren · Restaurant with the VAT breakdown, runs the fraud check (clear), and the customer confirms. Pay writes a local record with a PACS.008 draft whose purpose code is SCVE; Business writes kvitto K-000412. Two honest ledgers, one agreed payment.

6The tax engine & settlement

Two pieces sit alongside the core flow: the tax engine that helps a wallet holder stay compliant, and the bilateral settlement that actually moves value.

The tax engine

The SDK's tax module is a jurisdiction-aware crypto-asset tax engine — cost-basis tracking, holding-period relief, loss offset, and position & annual reports exportable as K4 or CSV. The rules are defined in FUTURECHAIN_TAX_RULES.md and hot-loaded as YAML, so a jurisdiction's rules can change without an app rebuild. It is IN PROGRESS — the schema and the Sweden rules are done; cost-basis methods and other jurisdictions are still in draft. It is surfaced today inside the ANTON Comm wallet.

Settlement

The apps agree on the payment and record it — they do not move the money. Settlement is bilateral: the merchant settles directly with Safello, which runs the blockchain node. The KYC model is merchant-side. Settlement integration is currently SPEC — the reference code is archived. The apps are designed to be honest local ledgers regardless of when settlement wires up.

7Best practices

✓ Do
  • Read the whole review screen — the URI is the contract, so every field matters.
  • Trust the FTC amount; treat the local-currency estimate as a guide only.
  • Expect a fresh QR if one has expired — that's the design, not a fault.
  • Check Build status before relying on signing or settlement.
  • Keep both ledgers — the merchant's kvitto and the payer's record are independent receipts.
✕ Don't
  • Don't treat a PACS.008 draft as a signed instrument today — it isn't yet.
  • Don't expect a payment server to be online — the URI is self-contained.
  • Don't assume the apps settle the money — settlement is bilateral, off-app.
  • Don't hand-parse a futurechain:pay URI — use reference.decode().
  • Don't rely on tax output for a jurisdiction still in draft — check the engine's status.
