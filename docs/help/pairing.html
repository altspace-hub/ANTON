Pairing & enrollment

Before a phone can do anything with your ANTON Local instance, it has to become trusted. ANTON does this with a short, deliberate ritual built on Ed25519 keys and a QR code — no passwords, no central authority, no account server. This page walks through exactly how it works.

1What pairing is

Pairing — formally enrollment — is the one-time act of teaching an ANTON Local instance that a particular phone belongs to a particular person, and teaching the phone how to reach that instance securely ever after.

It is what stands between "a phone on the network" and "a phone allowed to read your approvals, run modules and receive your push notifications." It is the foundation under ANTON Companion, and the same Ed25519 identity model underpins ANTON Comm, Business and Pay.

🔑

Key-based

Each side proves itself with an Ed25519 signature — there is no shared password to leak.

📷

QR-anchored

Trust is bootstrapped in person, by scanning a short-lived QR on the instance's screen.

🏛

No authority

No certificate authority, no account server. The instance is its own root of trust.

2How to think about it

🧭The mental model

Think of pairing as a handshake you do once, in person. The QR code on the instance's screen is the moment of trust — by being physically in front of it, you confirm "this phone, this instance, this person." Everything after that is just two keys recognising each other. There is no authority to ask, because the instance is the authority for its own devices.

Three ideas carry the whole design:

  • Trust is established once, then it's just keys. The QR scan is the only moment that needs a human and a physical screen. After it, the phone holds a device certificate and the instance holds the phone's public key — they authenticate each other forever without anyone re-confirming anything.
  • The keypair is born on the phone and never leaves it. The phone generates a fresh Ed25519 keypair during enrollment. The private key goes straight into the OS secure element (iOS Keychain / Android Keystore) and is never transmitted — not to the instance, not to a relay, not anywhere.
  • The package is deliberately short-lived. The enrollment QR is valid for 60 seconds. A pairing offer that isn't used almost immediately simply expires — there is no long-lived secret sitting around to be stolen.
💡Why no central authority is a feature

A traditional system has an account server that everyone must trust and that becomes a single juicy target. ANTON has none. Your instance vouches only for its own devices; a different instance is a completely separate trust domain. There is nothing central to breach, and nothing central to take down.

3The enrollment ritual, step by step

Enrollment is a four-step exchange. The instance offers, the phone mints a key, the phone proves itself, the instance issues a certificate.

  1. The admin issues an enrollment package

    On ANTON Local, the admin opens Connect a device. The instance builds a package — a one-time token and nonce, its own Ed25519 and X25519 public keys, a self-binding signature, the TLS cert fingerprint, relay endpoints, and an optional 6-digit out-of-band code — and renders it as a QR with a 60-second time-to-live.

  2. The phone scans & mints a fresh keypair

    The phone reads the QR. It generates a brand-new Ed25519 keypair and writes the private key into the biometric-protected Keychain (iOS) or Keystore (Android). That private key never leaves the secure element.

  3. The phone signs the challenge & posts it

    The phone signs the string ${token}.${nonce}.${publicKey} with its new private key and POSTs the result to /api/app/enrollment/complete, along with its device public key and — if the admin set one — the 6-digit confirmation code typed by the user.

  4. The server verifies & issues a certificate

    The instance checks the signature against the public key, checks the confirmation code, and confirms the token and nonce are unused and unexpired. On success it issues a device certificate and a 30-day session token. The phone biometric-locks both. The phone is now paired.

⚠The 6-digit code is your out-of-band check

The optional confirmation code is shown on the instance and typed into the phone by a human. It defends against the case where someone photographs the QR from across a room — they'd have the QR but not the code. For any device that isn't physically in your hand the whole time, set a confirmation code.

How it works app-enrollment-service.ts & the API +

The server side lives in server/services/app-enrollment-service.ts. It builds the EnrollmentPackage — token, nonce, instance_pubkey, instance_cert_fp, endpoints ({ lan, wan, mdns_name }), an optional transport kind (public_https default, or mesh with ranked relay_endpoints) and the optional confirmation_code. The matching routes are mounted under /api/app/* — the device POSTs the signed completion to /api/app/enrollment/complete. A legacy register-simple flow remains as a Web Crypto fallback for clients that cannot do native Ed25519.

Three tables back the ritual (migrations 094 + 130 + 131): app_enrollment_tokens holds the short-lived offer (with its confirmation_code); app_devices records each Ed25519-paired phone and its device certificate; instance_identity stores the instance's own keypair. Enrollment is BUILT — see Build status — with multi-instance, biometric locking and revocation all in place; 16 tests in tests/app/enrollment-link.test.ts and enrollment-service.test.ts cover URL parsing and the signature contract.

How it works Encrypting the instance key at rest +

The instance's own Ed25519 private key — the root of trust for every paired device — sits in the instance_identity table. If you set the environment variable INSTANCE_KEY_ENCRYPTION_KEY to a 32-byte hex value, that private key is stored AES-256-GCM encrypted in instance_identity.privkey_encrypted.

Without the variable the service still works, but it stores the key in plaintext and writes a one-time warning to the log. For any deployment beyond a personal laptop, set INSTANCE_KEY_ENCRYPTION_KEY — it is the difference between "someone with the database has your instance identity" and "someone with the database has ciphertext."

4Worked example — pairing a phone

An office wants to give an analyst Companion access to the shared ANTON Local instance.

  1. Admin opens "Connect a device"

    ANTON Local renders a QR and shows a 6-digit code: 417-293. A 60-second countdown starts.

  2. Analyst scans within the minute

    Companion decodes the package and immediately generates a fresh Ed25519 keypair into the Android Keystore.

  3. Analyst types 417-293 and confirms

    Companion signs token.nonce.publicKey and POSTs it with the code to /api/app/enrollment/complete.

  4. The instance issues the certificate

    Signature and code check out. A device certificate and a 30-day session token come back; Companion biometric-locks them. The analyst's phone now appears in the instance's device list and can be revoked any time.

📌What the analyst's phone holds afterwards

After pairing, the phone holds: its own Ed25519 private key (in the Keystore, never sent anywhere), a device certificate signed by the instance, a 30-day session token, and the instance's public keys + relay endpoints so it knows how to reach it. The instance holds only the phone's public key. Neither side ever saw the other's secret — which is exactly the point.

5Multi-instance & the contact hash

One phone can pair with several ANTON Local instances — a personal laptop, an office instance, a client's instance. Each pairing is fully independent: a separate keypair, a separate certificate, a separate trust domain.

Switching between instances

Companion keeps the paired list in src/app/services/instances.ts. A Wallet-card-style switcher (InstanceSwitcher / InstanceTopBar) makes the active instance unambiguous — you always know which ANTON you're talking to. setActiveInstanceAsync() is race-free so a fast switch can't leave you half-connected.

The contact hash

Every ANTON identity has a shareable, privacy-preserving address in the format ANTON-XXXX-XXXX-XXXX-XXXX — a contact hash derived from the Ed25519 public key. It is safe to print, message or read aloud: it reveals an address to reach you, never a secret. The same format is used across Companion, Comm, Business and Pay.

💡One phone, many ANTONs

Because each pairing is its own trust domain, losing access to one instance — revoking the device, say — has no effect on the others. And because the contact hash is just an address, you can share it freely; it is the QR ritual, not the hash, that grants any actual trust.

6Best practices

✓ Do
  • Pair in person — be physically in front of the instance's QR.
  • Set a 6-digit confirmation code for any non-personal device.
  • Set INSTANCE_KEY_ENCRYPTION_KEY on any shared deployment.
  • Scan promptly — the QR expires after 60 seconds by design.
  • Revoke a device from the instance's device list the moment a phone is lost.
✕ Don't
  • Don't photograph an enrollment QR to "pair later" — it will have expired.
  • Don't share a QR over a chat app — pairing is meant to be face to face.
  • Don't reuse one pairing across phones — each device mints its own keypair.
  • Don't treat the contact hash as a secret — it's an address, not a key.
  • Don't skip the confirmation code on devices that leave your hands.
