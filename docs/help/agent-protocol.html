The Agent Protocol & portals

Everything so far connected a phone to an instance. This page is about the next layer up: how whole ANTON instances talk to each other — exchanging signed, encrypted knowledge bundles directly, peer to peer — and how portals make an instance discoverable to others.

1What the Agent Protocol is

The ANTON Agent Protocol — AAP — is how one ANTON instance talks to another. Not a phone to an instance, but a full instance to a full instance: two peers, each with its own pillars, modules and data, exchanging information directly.

What they exchange is .anton bundles — the same portable knowledge format ANTON uses everywhere. A contact bundle, an evidence pack, a market thesis, a Risk Atlas pack, a portal descriptor: all of these can travel from one instance to another over AAP, signed and encrypted, with no server in the middle.

🧭Where this sits in the vision

AAP is the concrete foundation of layer 4 of the ANTON vision — Collaborative Intelligence. Layer 1 is the individual instance; layer 3 is the human network (Community messaging); layer 4 is ANTON-to-ANTON collaboration, where instances delegate, share and verify each other's work. AAP is the wire it runs on. It is honestly marked IN PROGRESS — see Build status.

2How to think about it

🧭The mental model

Think of AAP as two ANTONs shaking hands and trading sealed folders. Each instance proves who it is with an Ed25519 signature, the two agree a shared secret nobody else holds, and then they pass .anton bundles back and forth — each one a sealed, encrypted folder that only the other instance can open. There is no broker, no account, no central directory the conversation depends on.

Three ideas frame the rest of the page:

  • It is symmetric. Unlike pairing — where a phone enrolls with an instance — AAP is peer to peer. Either instance can initiate; both speak the same protocol; neither is subordinate.
  • Identity is the contact hash, again. An instance is addressed by the same ANTON-XXXX-XXXX-XXXX-XXXX contact hash used everywhere in the suite, and proves ownership of it with an Ed25519 signature on every message.
  • Discovery is the careful part. Talking to an instance you already know is built. Letting strangers find your instance — public portal discovery — is on a deliberate roadmap with a legal review gating launch. The page is honest about that line.
💡Why instances talk in bundles, not API calls

A .anton bundle is self-contained and signed — it carries its own provenance. So when instance A sends instance B an evidence pack, B doesn't just receive data; it receives a verifiable artifact it can store, re-share or audit later. Collaboration that survives being passed along is what makes layer 4 more than a chat protocol.

3The AAP handshake & bundles

AAP wire format v1 is locked. The transport is a WebSocket over wss:// at the path /aap/v1, and on a local network an instance advertises that endpoint over mDNS so nearby peers can find it without configuration.

Every AAP message is a signed envelope with a fixed shape — version v: 1, a type, an id, a timestamp ts, the sender's contact hash from, a nonce, a payload, and an Ed25519 sig. The message types are:

TypeRole
HELLOInitiator opens — declares identity and the capabilities it offers.
WELCOME / REJECTResponder accepts (and names accepted capabilities) or declines.
BUNDLEAn AES-256-GCM-encrypted .anton bundle body.
ACKConfirms a bundle was received.
PING / PONGKeep-alive.
ERROR / GOODBYESignal a fault, or close the session cleanly.

The cryptography is layered: an Ed25519-signed HELLO/WELCOME handshake authenticates both peers; an X25519 ECDH exchange derives a shared secret; that secret keys AES-256-GCM for every BUNDLE body. Each envelope also carries a replay-protected nonce, so a captured message cannot be re-sent later.

How it works aap-transport-server.ts & the session +

The server side is server/services/aap-transport-server.ts: a WebSocketServer mounted at /aap/v1 that implements the HELLO/WELCOME handshake, BUNDLE dispatch, ACK, PING/PONG, ERROR and GOODBYE. It does not re-implement crypto — Ed25519 verification, the X25519 exchange and AES-256-GCM bundle decryption all live in community-crypto.ts; the transport file only orchestrates the protocol.

Each accepted peer becomes a SessionState holding the peer's contact hash and pubkey, the list of acceptedCapabilities, and the derived sharedKeyHex (X25519 → HKDF) used to decrypt BUNDLE bodies. The server enforces a clock-skew tolerance of five minutes on timestamps and only accepts a fixed set of SUPPORTED_CAPABILITIES — evidence-pack-publisher, market-thesis-share, risk-atlas-export, portal-publisher, career-profile-exchange, humanitarian-deployment, hardware-share and more. The outbound side is aap-transport-client.ts, used to send bundles to wss://peer/aap/v1.

4A bundle exchange, step by step

Here is one instance sending another a Risk Atlas pack over AAP.

   INSTANCE A  (sender)                          INSTANCE B  (receiver)
   ──────────────────────                        ──────────────────────
   open wss://B/aap/v1                                    │
        │                                                 │
        │ ──── HELLO ─────────────────────────────────────▶
        │      v:1 · from: ANTON-A · capabilities          │  verify Ed25519 sig
        │      · nonce · Ed25519 sig                        │  check ts skew (±5m)
        │                                                  │  check nonce unseen
        │ ◀─── WELCOME ────────────────────────────────────│
        │      accepted: [risk-atlas-export] · X25519 pk    │
        │                                                  │
        │ ═══ X25519 ECDH  →  HKDF  →  shared AES-256 key ══│  both sides derive
        │                                                  │  the same key
        │                                                  │
        │ ──── BUNDLE ─────────────────────────────────────▶
        │      AES-256-GCM( .anton risk-atlas pack )         │  decrypt · verify
        │      · fresh nonce · Ed25519 sig                   │  · store artifact
        │ ◀─── ACK ────────────────────────────────────────│
        │                                                  │
        │ ──── GOODBYE ────────────────────────────────────▶  session closed
  1. Instance A opens a session

    A connects to wss://B/aap/v1 and sends a HELLO — its contact hash, the capabilities it offers, a fresh nonce, all under an Ed25519 signature.

  2. Instance B verifies and welcomes

    B checks the signature against A's pubkey, confirms the timestamp is within the five-minute skew window and the nonce is unseen, then replies WELCOME naming the capabilities it accepts — or REJECT if it declines.

  3. Both sides derive a shared key

    An X25519 ECDH between the two instances, run through HKDF, produces an identical AES-256 key on each side. Nobody else can compute it.

  4. Instance A sends the bundle

    A wraps the .anton Risk Atlas pack in an AES-256-GCM BUNDLE envelope, with its own fresh replay-protected nonce and signature, and sends it.

  5. Instance B decrypts, verifies and acks

    B decrypts the body, verifies the signature, stores the bundle as a verifiable artifact, and replies ACK. A GOODBYE closes the session cleanly.

📌Example — sharing a Risk Atlas pack with a partner firm

A consultancy has built a sector-specific Risk Atlas pack and wants a partner firm's ANTON instance to use it. The consultancy's instance opens AAP to the partner's /aap/v1, sends HELLO offering risk-atlas-export; the partner's instance recognises the contact hash, replies WELCOME. One BUNDLE later, the partner holds the pack — encrypted in transit, signed so its origin is provable, ready to load into their own Risk Atlas. No file was emailed, no portal was public, no third party saw the content.

5Portals & the registry protocol

AAP lets two instances talk once they know each other. Portals are how an instance becomes findable in the first place. A portal is a user-built ANTON web space that is simultaneously a human-facing site and a machine-readable AAP endpoint, described by a capability descriptor.

The registry protocol

To list a portal so others can discover it, an instance submits a signed record to a registry. The registry protocol enforces three things: canonical JSON (RFC 8785 / JCS — so a signature round-trips identically on both ends), signed envelopes (every submitted record carries an Ed25519 signature), and homoglyph defence (a portal can't register a name that visually impersonates another).

The transparency log

The registry is hosted by the relay process and keeps an append-only, signed transparency log. A registry client verifies portal records against that log, so a registry operator cannot quietly insert or alter an entry without it being detectable. Trust is verifiable, not assumed.

⚠What is built, and what is on the roadmap

Local portals are complete — building, publishing, visiting and invoking a portal on instances you already know works end to end. But cross-instance public discovery — strangers finding your portal through a public registry — is on a deliberate 6-phase roadmap with a legal review gating launch. The protocol pieces (canonical JSON, signed envelopes, homoglyph defence, transparency log) exist; turning on open public discovery is a separate, gated decision. See Build status for exactly where the line is.

How it works registry-protocol/ & registry-client/ +

server/services/registry-protocol/ holds the wire rules: canonical-json.ts wraps RFC 8785 canonicalisation via the vetted @truestamp/canonify library (hand-rolling canonicalisation is a known source of subtle cross-implementation bugs); envelope.ts builds and verifies the signed records; homoglyph.ts runs two confusable-name checks — hasRiskyMixedScript() blocks names mixing Latin with a confusable script (Cyrillic, Greek, Armenian, Cherokee), and computeSkeleton() does a UTS #39 confusable-skeleton reduction so the server can reject a registration whose skeleton already exists.

server/services/registry-client/ is the consuming side — relay-submit.ts submits portals to the relay-hosted registry, log-verifier.ts + sth-gap-check.ts verify the signed transparency log, trust-store.ts and nonce-store.ts manage trusted keys and replay protection, and cache.ts / rate-limiter.ts / audit-writer.ts handle the operational edges. The portal capability model itself — the 12-verb capability taxonomy and descriptor schema — lives under server/services/capability-descriptor/ and server/services/portals/.

6Best practices

✓ Do
  • Use AAP to share .anton bundles with instances you already trust.
  • Treat a received bundle as a verifiable artifact — its signature proves origin.
  • Let mDNS handle discovery of peer instances on the same network.
  • Check Build status before relying on public portal discovery.
  • Keep instance Ed25519 keys encrypted at rest — they sign every AAP message.
✕ Don't
  • Don't assume public cross-instance discovery is live — it's gated behind a legal review.
  • Don't hand-roll canonical JSON — signatures will silently fail to round-trip.
  • Don't accept a bundle whose signature you can't verify against a known key.
  • Don't treat AAP like pairing — it's symmetric, peer to peer, with no subordinate side.
  • Don't expect a registry operator to be trusted blindly — verify against the transparency log.

AAP and portals are ANTON's proof that instances can collaborate without a central server in the middle — the working first step into vision layer 4. For an honest, component-by-component map of what is built, partial, stubbed or still spec, see the Build status page next.
