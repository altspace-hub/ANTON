Specialized Agents — standing AI personas

A module is a one-shot expert task. A Specialized Agent is something more durable: a named AI persona that stays on, holds a conversation, routes questions, reaches into live systems through tools, and escalates to a human when it should. Agents are how ANTON staffs a function — support, sales, HR — rather than answering a single question.

1What a Specialized Agent is

A Specialized Agent is an autonomous AI persona with four things of its own: a system prompt that defines who it is, knowledge packs it draws on, routing rules that decide what it handles and what it passes on, and an escalation policy that says when a human must step in.

Agents sit at Layer 4 of ANTON's vision — Collaborative Intelligence. They are managed from the Agent Hub, and a single ANTON instance can run several at once: a support agent, a sales agent, an HR agent, a travel agent — each a distinct persona staffing a distinct function.

🎭

A standing persona

Always on, holds context across a whole conversation, not a single turn.

🔌

Tool-equipped

Reaches live systems — APIs, databases, calendars — through connectors.

🚦

Knows its limits

Routing rules and an escalation policy decide when to hand off to a human.

2How to think about it — agent vs module

🧭The mental model

A module is a specialist you call in for one job — brief it, get a deliverable, done. A Specialized Agent is a team member you hire — it has a role, it stays, it handles whatever comes to its desk, it uses the tools its role needs, and it knows when a question is above its pay grade and escalates. If the work is a task, build a module run. If the work is a function, build an agent.

Expert moduleSpecialized Agent
LifetimeOne run, then it's overStanding — runs until you turn it off
ConversationA single prompt and responseAn ongoing, multi-turn conversation with memory
ToolsKnowledge sources onlyLive connectors — API, database, email, calendar, CRM, ERP
RoutingYou pick the moduleThe agent decides what it handles vs escalates
Best for"Draft this", "assess that""Handle our tier-1 support", "qualify inbound leads"
💡They are not rivals

An agent often uses module-style expertise inside its conversation — the difference is the wrapper, not the intelligence. Reach for a module when you personally want one deliverable; reach for an agent when something needs to be handled repeatedly, by itself, with tools and a hand-off path.

3The anatomy of an agent

Every agent profile is four parts. Get these right and the agent behaves predictably; get them vague and it drifts.

   ┌──────────────────────── AGENT PROFILE ────────────────────────┐
   │                                                                │
   │   SYSTEM PROMPT          who it is · tone · what it must        │
   │                          and must not do                       │
   │                                                                │
   │   KNOWLEDGE PACKS  ───▶   the .anton bundles it reasons from    │
   │                                                                │
   │   ROUTING RULES    ───▶   what it answers itself                │
   │                           what it passes on                     │
   │                                                                │
   │   ESCALATION       ───▶   the trigger + the human it hands      │
   │   POLICY                  off to                                │
   │                                                                │
   │   CONNECTORS  ┌── rest_api ── webhook ── database ──┐           │
   │               └── email ── calendar ── crm ── erp ──┘           │
   │                                                                │
   └────────────────────────────────────────────────────────────────┘
              │                                    │
              ▼                                    ▼
      agent_conversations                  agent_audit_log
      (multi-turn memory)                  (every action recorded)
  • System prompt — the agent's identity, tone and boundaries. This is the single most important field; write it as you would a job description.
  • Knowledge packs — the .anton bundles the agent reasons from, exactly like a module's knowledge layer.
  • Routing rules — what the agent answers directly versus what it forwards. This keeps the agent inside its competence.
  • Escalation policy — the condition under which a human is brought in, and who that human is.
How it works Profiles, conversations & the data model +

Migration 111_specialized_agents.sql defines six tables: agent_profiles (the persona, prompt, routing and escalation config), agent_conversations and agent_messages (multi-turn memory), agent_connectors (the tools an agent may use), agent_templates (starting points) and agent_audit_log (every action the agent takes, recorded).

CRUD on profiles runs through server/services/agent-service.ts. Each conversation turn is handled by agent-processor.ts, which manages the dialogue and routes any tool calls. The REST surface is server/routes/agents.ts — GET/POST /agents, /agents/:id, plus the public directory and query endpoints covered in §6.

4Connectors — reaching live systems

What separates an agent from a chatbot is that it can act. Connectors are the agent's tools — typed channels to live systems. Seven connector types are available.

Connector typeLets the agent…
rest_apiCall an external REST API to fetch or send data
webhookTrigger an outbound webhook into another system
databaseRun read-only queries against a database
emailSend and read email
calendarCheck availability and create events
crmLook up and update CRM records
erpReach into an ERP for orders, stock, invoices
⚠Credentials are vaulted; database access is read-only

Connector credentials are never stored in plain text — they are encrypted in ANTON's credential vault and decrypted only at call time. Database connectors are deliberately read-only: an agent can look something up but cannot mutate your database directly. Anything that changes state should go through a connector you control, with the agent's escalation policy gating the sensitive cases.

How it works The connector executor +

When the agent's conversation produces a tool call, server/services/agent-connector-executor.ts carries it out — a live API call, an outbound webhook, or a read-only database query. Credentials come from credential-vault.ts, decrypted only for the duration of the call. Every connector invocation is written to agent_audit_log, so an agent's actions are fully traceable after the fact — which is what makes an autonomous agent safe to run in a regulated setting.

5Creating an agent, step by step

You build agents in the Agent Hub. You can start from a template, or describe the agent in plain language and let the agent builder draft the whole configuration for you.

  1. Open the Agent Hub

    The management surface for every agent on this instance — create, edit, enable, disable.

  2. Describe the agent, or pick a template

    Type what you want — "a first-line support agent for our software product" — and the agent builder generates a draft profile: system prompt, suggested knowledge packs, routing and escalation.

  3. Review & tighten the system prompt

    This is the agent's identity. Make the boundaries explicit — what it must never promise, what tone it holds.

  4. Attach knowledge packs

    Give the agent the .anton bundles it should reason from — your product docs, your policies.

  5. Add connectors

    Wire the tools the role needs — a database connector to look up orders, a calendar to book a callback. Credentials go into the vault.

  6. Set routing & escalation

    Define what the agent handles itself and the trigger that hands a conversation to a named human.

  7. Test, then enable

    Run trial conversations from the Hub. When it behaves, enable it — and check agent_audit_log periodically.

📌Example — a first-line support agent

You want an agent to handle tier-1 support for your software. You describe it to the agent builder, which drafts a profile. You tighten the system prompt ("be warm, never promise a refund, never speculate on a delivery date"), attach the product-docs.anton knowledge pack, and wire a read-only database connector so it can look up a customer's order status and a calendar connector to book a callback. The routing rule says it answers how-to and order-status questions itself; the escalation policy says anything mentioning billing, refunds or a complaint goes straight to the human queue. A customer asks "where's my order?" — the agent queries the database and answers. A customer asks for a refund — the agent escalates, politely, and a person picks it up. Every step is in agent_audit_log.

6Remote agents across instances

Agents are not confined to your own instance. An agent can be published to a public directory, and other ANTON instances can discover it and route a query to the best-matching remote agent. This is the concrete first step of Layer 4 — ANTON-to-ANTON collaboration.

The flow is symmetric: /agents/public/directory lists the agents an instance offers, and /agents/public/query accepts a question and routes it to the agent best suited to answer. A support agent on one instance can field a question that originated on another — without either side exposing its internals.

💡Where this is going

Cross-instance agents are in progress — the foundation is built and the discovery and query endpoints work, but Layer 4 of the Agent Protocol vision is still maturing. Check Build status for exactly where remote agent collaboration stands today before depending on it for production work.

How it works The agent builder & remote discovery +

server/services/agent-builder.ts turns a plain-language description into a full agent configuration — system prompt, suggested knowledge, routing and escalation — which you then review and edit. remote-agent-client.ts handles the cross-instance side: it discovers agents on peer instances and routes a query to the best match. The public surface is /agents/public/directory and /agents/public/query in server/routes/agents.ts; the agent UI is src/pages/agents/AgentHubPage.tsx.

7Best practices

✓ Do
  • Build an agent for a function; use a module for a one-off task.
  • Write the system prompt like a job description — explicit boundaries.
  • Set a clear escalation policy before you enable the agent.
  • Keep database connectors read-only; gate state changes behind escalation.
  • Test with trial conversations, then review agent_audit_log regularly.
✕ Don't
  • Don't ship the agent builder's first draft unread — always tighten the prompt.
  • Don't give an agent a connector its role doesn't need.
  • Don't leave the escalation policy vague — an agent with no hand-off path will overreach.
  • Don't depend on cross-instance remote agents for production before checking build status.
  • Don't store connector credentials anywhere but the vault.
★An agent is staff, not a feature

The agents that work well are the ones treated like a new hire: a clear role, a clear scope, the right tools, a manager to escalate to, and a record of what they did. The agents that go wrong are the ones given a vague prompt and broad access "to be helpful". Define the job tightly — the agent will do exactly that job, tirelessly.
