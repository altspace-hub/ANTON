ANTON Mesh & the relay

When your phone can't reach your ANTON Local instance directly, a small relay server bounces encrypted traffic between them. This page explains what the relay is, the one thing it can never do — read your traffic — and how to think about trusting it.

1What the relay is

A phone app — ANTON Companion or ANTON Comm — needs to reach a server somewhere. There are two ways that can happen:

→

Direct HTTPS

The phone talks straight to your ANTON Local on the LAN, or on a public URL. Simplest path — no relay involved at all.

↔

Mesh relay

When the instance has no public address — a laptop at home, behind a router — a relay in the middle forwards the traffic for both sides.

The ANTON Mesh relay is the second path. It is a tiny Node.js process — a WebSocket broker — that exists for one reason: to connect two parties who otherwise cannot find each other. It replaces the Cloudflare Tunnel that earlier builds relied on, so the whole rail can be owned and audited by the people who run it. The reference implementation lives in relay/, is about 5,900 lines of TypeScript, and is licensed Apache-2.0 so anyone can host one.

💡The key fact, up front

The relay carries opaque ciphertext. The encryption is set up directly between your phone and your instance — the relay is never a party to it. It moves sealed envelopes; it cannot open them. Everything else on this page is a consequence of that one design choice.

2How to think about it

🧭The mental model

Think of the relay as a dumb, blind postbox. It accepts sealed envelopes and hands them to whoever is waiting on the other side of the same box. It cannot read what's inside, it cannot write a convincing fake, and it cannot decide to deliver your mail somewhere else. It can see that an envelope passed through, and it can refuse to carry it — but that's the full extent of its power.

Two ideas make the rest of this page click:

  • Encryption ends at the two real parties. The phone and the instance perform a Noise-IK handshake with each other. The relay only ever sees the result: ENVELOPE frames it cannot decrypt. This is end-to-end encryption in the literal sense — the "ends" are the two devices, not the relay.
  • The relay is untrusted by design. You do not have to believe the relay operator is honest. The protocol is built so that a malicious relay can annoy you (drop traffic, watch metadata) but can never read, impersonate or misdeliver. That is why self-hosting is optional, not required — a public relay is safe to use.
⚠What the relay is not

The relay is not a server that runs ANTON. It holds no documents, no sessions, no AI. It is pure plumbing. If the relay goes down, your data is untouched — you simply lose the indirect path and fall back to direct HTTPS on the LAN.

3The trust model — what it can and cannot do

The honest way to reason about any relay is to name its powers exactly. Here they are.

The relay CAN…The relay CANNOT…
See metadata — which instance id connected, when, and how much traffic flowedDecrypt any traffic — the Noise-IK keys never reach it
Cause denial of service — drop, delay or refuse to forward framesImpersonate an instance — a binding signature is checked on every HELLO
Observe connection lifetimes and approximate message sizesMisroute traffic — direction tags + instance-id matching pin each leg
Be replaced — you can run your own and bypass a public one entirelyReplay an old proof onto another relay — the proof is bound to one relay_url
🧭How to weigh this

A relay you don't run can learn that your phone talked to your instance and roughly how much — never what. If even that metadata matters to you, the answer is simple: run your own relay (§5). For most people, a public relay carrying sealed envelopes is an entirely reasonable trade.

The cipher suite

The phone↔instance tunnel uses Noise IK with this exact suite:

   Noise_IK_25519_ChaChaPoly_BLAKE2b
   ───────────  ─────  ──────────  ───────
        │          │        │         │
        │          │        │         └─ BLAKE2b      — hashing in the handshake
        │          │        └─ ChaChaPoly             — ChaCha20-Poly1305 AEAD
        │          └─ Curve25519 (X25519)             — ephemeral Diffie-Hellman
        └─ IK pattern   — initiator Knows responder's static key in advance

The IK pattern matters: the phone already knows the instance's static public key (it learned it during pairing), so the handshake authenticates the instance from the very first message. Long-term identity is Ed25519; the ephemeral key exchange is X25519.

How it works The wire frame & instance-id matching +

Every relay message is a frame defined in relay/src/frame.ts: a 1-byte version (0x01), a 1-byte type, a 3-byte big-endian payload length, then the payload. Frame types include HELLO_INSTANCE (0x01), HELLO_PHONE (0x02), ACK_*, PING/PONG, DIAL_INSTANCE (0x07 — an instance dialing a peer instance), ERROR (0x0F) and ENVELOPE (0x10 — the opaque ciphertext the relay just forwards).

The relay matches the two legs of a connection by instance id. Per spec §1.5, instance_id = sha256(instance_X25519_static_pubkey)[0..16) — the first 16 bytes of the SHA-256 of the instance's static X25519 public key (deriveInstanceId in relay/src/primitives.ts). Because the id is derived from a key the relay can verify a signature against, the relay cannot be tricked into pairing a phone with the wrong instance.

How it works The 6-step HELLO verification +

relay/src/hello.ts runs the spec §3.2 six-step verification on every HELLO_INSTANCE. It is the relay's one real security duty, and it guards three attacks: instance squatting (a stranger claiming your instance id — closed by the binding signature), proof replay across relays (closed by binding the proof to this relay's relay_url), and bad signatures (closed by checking both binding_sig and proof_sig).

Failures raise a typed HelloVerificationError with a named code — BAD_HELLO (0x0002) for a malformed payload, mismatched id, bad binding or wrong relay_url, and INVALID_PROOF (0x0003) for a bad timestamp, bad signature or replay. The relay closes the connection rather than guessing. The Comm app uses a parallel set of frame types (HELLO_COMM 0x20 … DELIVER_COMM 0x23) so one relay process can carry both instance traffic and Comm messages — a frame-type byte keeps the two cleanly separated.

4A relayed request, step by step

Here is exactly what happens when your phone, paired to a home instance with no public address, opens its approvals inbox through the relay.

     ANTON COMPANION                RELAY                 ANTON LOCAL
     (your phone)            (blind postbox)            (home laptop)
          │                         │                         │
          │                         │ ◀──── HELLO_INSTANCE ────│  1. instance
          │                         │       (binding sig,      │     registers,
          │                         │        relay_url, id)    │     id derived
          │                         │ ──── ACK_INSTANCE ──────▶│
          │                         │                         │
          │ ──── HELLO_PHONE ──────▶ │  2. phone asks for       │
          │      (instance id)       │     that same id         │
          │ ◀──── ACK_PHONE ─────────│  3. relay MATCHES the    │
          │                         │     two legs by id       │
          │                         │                         │
          │ ══════ Noise IK handshake (end to end) ═══════════▶ │  4. phone &
          │ ◀═════ relay forwards bytes, cannot read them ═════ │     instance
          │                         │                         │     share keys
          │                         │                         │
          │ ═══ ENVELOPE (sealed ciphertext) ═════════════════▶ │  5. real
          │ ◀══ ENVELOPE (sealed ciphertext) ══════════════════ │     traffic
          │                         │                         │
       inbox shown          relay saw 2 ids +           request handled
                            byte counts — nothing more
  1. The instance registers

    Your ANTON Local opens a long-lived WebSocket to the relay and sends HELLO_INSTANCE — its instance id plus a binding signature proving it owns the key behind that id. The relay verifies and holds the connection.

  2. The phone asks for that id

    Companion sends HELLO_PHONE naming the instance id it learned at pairing. The relay looks for a registered instance leg with that id.

  3. The relay matches the two legs

    Finding both, the relay now has a pair. From here it does exactly one job: copy bytes from one leg to the other.

  4. Phone and instance handshake — through, not with, the relay

    The Noise-IK handshake runs end to end. The relay forwards the handshake bytes but is not a participant; it ends up holding no keys.

  5. Real traffic flows as sealed envelopes

    Every subsequent message is an ENVELOPE frame of opaque ciphertext. Your approvals inbox loads. The relay saw two instance ids meet and counted some bytes — and learned nothing else.

📌Example — approving a payment from the train

Your ANTON Local is a laptop at home with no public URL. On the train, you open Companion to approve a flagged checkpoint. Companion can't reach the laptop directly, so it connects to wss://relay.futurechain.eu, names your instance id, and the relay matches it to the laptop's already-registered leg. A Noise-IK tunnel forms end to end; the checkpoint and your Ed25519-signed approval cross as sealed envelopes. The relay operator could tell that some phone reached your instance at 14:02 — never that it was an approval, nor what it approved.

5Running your own relay

Because the relay is Apache-2.0 and self-hosting is a first-class path, an organisation that wants zero third parties on the rail can run its own. There are three deployment routes, in order of operational simplicity.

Docker

Recommended for self-hosters. A multi-stage Alpine image (~120 MiB). The bundled docker-compose.yml runs a read-only rootfs, drops all capabilities and sets memory/CPU limits.

systemd

Bare-metal, single-relay deployments. Runs as a dedicated anton-relay system user with no shell and no home directory.

Bare Node

For development and testing — RELAY_URL=wss://… node dist/index.js. TLS can terminate at the relay or at a reverse proxy in front of it.

The only required setting is RELAY_URL — the public WSS address the relay answers on, which clients bake into their connection list. TLS certs are optional (RELAY_TLS_CERT / RELAY_TLS_KEY) if you terminate TLS at the relay rather than at a proxy.

★When self-hosting is worth it

Self-host if metadata is sensitive — a relay you control sees the same metadata, but it's your metadata under your own retention rules. For a household or a single NGO, a public relay is perfectly fine: the envelopes are sealed either way. ANTON Mesh v0.1 deliberately targets households, NGOs and self-hosting SMEs — not enterprise fleets.

How it works What ships in relay/ +

The relay/ directory is a standalone package — its own package.json, Dockerfile, docker-compose.yml, systemd/ unit files and a RUNBOOK.md. Source under relay/src/: server.ts (the WS server), frame.ts (wire codec), hello.ts (HELLO verification), match.ts (instance-id leg matching), primitives.ts (Ed25519 / X25519 / SHA-256 via @noble), limits.ts (rate & size limits), audit.ts + metrics.ts (operational visibility), and registry/ + comm-registry.ts for the portal registry and Comm routing the same process also hosts.

The relay process is deliberately minimal: it accepts WebSocket connections, verifies HELLOs, matches legs and forwards bytes. It opens no outbound connections, reads no documents and runs no AI — which is exactly why a read-only, capability-dropped container is a comfortable fit. Build status: the relay is BUILT — a Phase 2 reference implementation with a peer-reviewed threat model.

6Best practices

✓ Do
  • Use direct HTTPS on the LAN when you can — it's the simplest path and skips the relay entirely.
  • Treat a public relay as safe for sealed traffic — that's the whole design.
  • Self-host a relay if connection metadata is genuinely sensitive to you.
  • Run the container as shipped — read-only rootfs, dropped capabilities.
  • Keep RELAY_URL stable; clients remember it.
✕ Don't
  • Don't expect the relay to "see" your data — it never can, so don't design as if it could.
  • Don't treat the relay as a backup of anything — it stores nothing.
  • Don't run a relay with broad capabilities or a writable rootfs — it needs neither.
  • Don't assume self-hosting changes the encryption — it doesn't; it only changes who sees metadata.
  • Don't panic if the relay is down — fall back to direct HTTPS.

The relay is the most invisible piece of the suite when it works, and the easiest to reason about once you hold the one fact: it is a blind postbox. Next, see how a phone first earns the right to be matched to your instance at all.
