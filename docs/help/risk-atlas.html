The Risk Atlas — a deterministic risk engine

The Risk Atlas turns risk assessment from an opinion into a calculation. It walks any business — a bakery or a bank — through seven stages from exposure to appetite, and the scores are computed by a fixed rule, not guessed by an AI. The result is a risk register you can defend to an auditor line by line.

1What the Risk Atlas is

The Risk Atlas is a workspace inside the Work pillar for building and maintaining a living risk register. It generalises the CASP BWRA (Business-Wide Risk Assessment) threat-path method into a universal causal-chain engine that any organisation can use, regulated or not.

Most risk registers are a spreadsheet of numbers nobody can explain six months later. The Atlas is different in one decisive way: the numbers are computed, not chosen. You supply the facts — what you are exposed to, how strong a control is — and a deterministic engine derives inherent risk, residual risk and appetite position. The AI writes the rationale around each number; it never decides the number itself.

⛓

Causal chains

Risk is modelled as a threat path — a story from exposure to harm, stage by stage.

🔢

Fixed arithmetic

Inherent, residual and appetite all come from one audited calculator.

📋

Audit-defensible

Every score traces to a rule and an input. Nothing is a black box.

2How to think about it

🧭The mental model

Think of the Atlas as a deterministic engine wrapped in LLM rationale. The engine is a calculator with locked rules: feed it the same inputs and it always returns the same residual score. The LLM's job is the words — describing a threat path in plain language, drafting a control description, explaining why a residual sits where it does. If an auditor asks "why is this a 4?", the answer is arithmetic, not judgement.

Two ideas explain almost every screen in the workspace:

  • A threat path is a sentence. "Cash-heavy takings (exposure) let a dishonest employee skim (threat) because there is no daily reconciliation (vulnerability), causing loss and tax misstatement (harm)." Every path you build should read as a coherent causal story.
  • The AI never moves a number. It can suggest exposures, draft threat paths, propose control descriptions — but the moment a score is set, the residual and appetite are pure arithmetic. This is non-negotiable and it is what makes the register hold up under scrutiny.
💡Why "weakest link" not "average"

Inherent risk is max(exposure, threat, vulnerability) — not an average. A path with low exposure today but a gaping vulnerability is still high-inherent, because the risk materialises the instant exposure changes. Averaging would hide that. The same worst-of logic governs controls: one weak control sinks the whole rollup for that path.

3The seven stages, walked

📌Example — a single threat path scored

A small café. Exposure: heavy cash takings, scored 4. Threat: employee skimming, credibility 3. Vulnerability: no daily till reconciliation, scored 4. Inherent risk = max(4, 3, 4) = 4. The café adds one control — a weekly (not daily) spot-check — graded Weak, reduction 0. Residual = 4 − 0 = 4 → outside appetite. Swap to a daily count with a signed log — an Adequate control, reduction −1 — and residual drops to 3, the boundary. The AI writes the wording on every line; the engine does the subtraction.

How it works The deterministic calculator +

server/services/risk-atlas/atlas-residual-calculator.ts is the engine — described in its own header comment as "the crown jewel of the methodology". It exposes pure functions: calculateInherent() returns max(exposure, threat, vulnerability); a control-rollup helper takes an arbitrary set of control strengths and returns the worst grade (empty list → absent); residual = inherent minus the reduction for that rollup (Strong −2, Adequate −1, Weak 0, Absent 0), clamped to [1, 5]; and appetite buckets the residual (1–2 within, 3 boundary, 4 outside, 5 unacceptable).

The file ships with 25 unit tests — every branch is covered and the header states plainly: "No LLM is involved." This is what makes the register reproducible: re-running the calculation can never silently change a score.

How it works The 18-table data model +

Migrations 125_risk_atlas_foundation.sql through 129_risk_atlas_addendum_review_fixes.sql define 18 tables. The core seven mirror the stages: risk_atlases, atlas_exposure_points, atlas_threat_paths, atlas_vulnerabilities, atlas_controls, atlas_inherent_scores, atlas_residual_scores. Around them sit atlas_appetite_statements, atlas_escalation_triggers, atlas_review_cycles, atlas_industry_packs, atlas_events, atlas_fcp_scope and atlas_cross_domain_path_bundles.

CRUD runs through atlas-service.ts with owner-bound mutations; every REST endpoint in server/routes/atlas.ts (~30 of them) is gated by ensureAtlasAccess(db, req, atlasId). Stage changes are appended to atlas_events via atlas-event-logger.ts, so the register carries its own audit trail.

4Industry packs & the FCP addendum

You rarely start an Atlas from a blank page. 25 industry packs ship as composable .anton overlays under data/risk-atlas/packs/. A pack pre-loads typical exposures, threat paths and severity benchmarks for a sector, so you begin with a sensible skeleton and edit rather than invent.

Pack kindExamplesUse
industrysme-general, fcp-bank, fcp-casp, sector-*The base for a whole organisation or sector
fcp-domainAML/CFT, sanctions, fraud, ABC, market abuse, tax-evasion facilitation, export controlsFinancial-crime overlays layered onto a base pack
overlayuniversal-fcp-coreCross-cutting content merged into any pack

Packs support parent inheritance — an FCP-domain pack can extend a base industry pack via parent_pack_id, and the loader protects against inheritance cycles. The FCP addendum adds two capabilities for financial-crime-obliged firms:

  • FCP scope — atlas_fcp_scope records which financial-crime domains are active for an Atlas, set with help from the fcp-scope-assessor module.
  • Cross-domain bundles — atlas_cross_domain_path_bundles groups threat paths from several domains into one causal "story" for the board pack, and computeCompanyAppetite() does a deterministic worst-of rollup per domain (Stage 7b).
💡Atlas in a Mission

For a regulated entity, the Atlas is one step in a larger programme. The mission template tmpl_amlr_readiness_v1 chains ten tasks — scope → Atlas → BWRA → gap analysis → policies → training → audit — with four human checkpoints. See Missions for how that orchestration works.

How it works The pack loader & inheritance +

atlas-pack-loader.ts loads, validates and merges packs. When a pack declares a parent_pack_id, getPackContent() resolves the chain depth-first and merges severity benchmarks and content, with explicit cycle protection so a malformed pack cannot loop. atlas-fcp-scope-service.ts owns FCP scope, the cross-domain bundles and the Stage 7b company-wide appetite rollup. Eight atlas-* modules under server/areas/risk/modules/ provide the per-stage LLM specialisations, orchestrated for AMLR Article 16 by business-wide-risk-assessment in the fcp area.

5Building an Atlas, step by step

The workspace is a five-tab shell. You move left to right; each stage feeds the next, and the computed stages update the moment an input changes.

  1. Create the Atlas & pick a pack

    Name the Atlas and choose a starting industry pack — sme-general for a small business, a sector pack for something specific. The pack seeds typical exposures and threat paths.

  2. Confirm exposures (Stage 1)

    Review the seeded exposure points, add what's missing, remove what doesn't apply, and score each 1–5. Be honest — this is the floor the chain is built on.

  3. Draw the threat paths (Stages 2–3)

    For each material exposure, describe how harm reaches you and the vulnerabilities on the way. Let the atlas-* modules draft the wording; you keep editorial control.

  4. Read the inherent scores (Stage 4)

    Inherent risk appears automatically per path. Nothing to enter — if a number looks wrong, an input is wrong.

  5. Link controls (Stage 5)

    Attach each mitigation to the vulnerability it addresses and grade it Strong / Adequate / Weak. Strong claims need real evidence — see §6.

  6. Review residual & appetite (Stages 6–7)

    Residual and appetite position compute live. Where a path sits outside appetite, write an action with an owner and a target date.

  7. Set a review cycle & export

    Schedule the next review and generate the board pack. The Atlas is now a living register, not a one-off document.

6Integrity rules & exports

An Atlas can drift — a residual creeps up, a Strong control loses its evidence, an outside-appetite path never gets an action. Six integrity rules run as pure functions over a snapshot of the Atlas and surface live findings on the workspace dashboard.

RuleFires when…
ATLAS-INT-001A residual of 4 or 5 has no appetite statement attached
ATLAS-INT-002A control graded Strong has no evidence (under 5 characters)
ATLAS-INT-003An outside-appetite path has no remediation action
ATLAS-INT-004An action exists but is missing an owner or a target date
ATLAS-INT-005/006Further consistency checks across escalation triggers and review cycles
⚠A Strong control is a claim, not a label

The integrity rules will not let you mark a control Strong and walk away. Strong carries a −2 reduction — the biggest move on the board — so it demands evidence: a policy reference, a test result, a sign-off. If you cannot point to proof, grade it Adequate. An honest Adequate beats an unevidenced Strong every time an auditor looks.

When the register is sound, atlas-export.ts produces the deliverables: a board-pack DOCX, a threat-path PDF, a heatmap SVG (the 5×5 appetite grid) and a portable .anton bundle you can share with a peer instance over the Agent Protocol.

How it works Integrity rules as pure functions +

atlas-integrity-rules.ts implements six Compliance-as-Code checks (ATLAS-INT-001…006) as pure functions over an Atlas snapshot — no I/O, easy to unit-test, deterministic. The workspace dashboard renders their findings live so a drifting register is visible without anyone running a report. Exports are assembled by atlas-export.ts; the heatmap SVG places each path on the 5×5 residual-by-likelihood grid produced by the calculator.

7Best practices

✓ Do
  • Start from the closest industry pack and edit — don't build from blank.
  • Write every threat path as a readable causal sentence.
  • Score exposures honestly; the whole chain rests on them.
  • Attach real evidence to any control you grade Strong.
  • Give every outside-appetite path an owner and a target date.
  • Set a review cycle so the Atlas stays a living register.
✕ Don't
  • Don't try to override a computed residual — it's arithmetic, fix the input.
  • Don't grade controls Strong to make the heatmap look better.
  • Don't average exposure, threat and vulnerability — the engine takes the max.
  • Don't ignore integrity-rule findings; they are the register telling you it has drifted.
  • Don't treat the AI's draft wording as final — review every line.
  • Don't let an Atlas go stale; a register with no review cycle is a document.
★The Atlas habit

The Risk Atlas earns its keep over time, not on day one. Revisit it on the review cycle, after every material change — a new product, a new jurisdiction, an incident — and let the engine recompute. Because the scores are deterministic, what changes between reviews is always traceable to a fact that changed. That traceability is the audit defence.
