# ADR-005 — Settlement delegation envelope format

**Status:** Open (BLOCKING settlement work)
**Owner:** Daniel Bardun

## The question

The merchant authorises `merchant-backend` to submit settlement
transactions on their behalf without per-transaction PIN entry. Spec
§12.3 defines the data model:

```typescript
interface SettlementDelegation {
  merchantId: string;
  walletAddress: string;
  safelloReceivingAddress: string;
  maxPerDayMicroFtc: bigint;
  validUntil: number;
  nonce: string;
}
```

But the spec doesn't define the **signing envelope** — how this payload
is canonicalised, hashed, and signed. The backend must be able to
re-derive the exact bytes the merchant's wallet signed and verify the
signature with the public key.

## Options

1. **EIP-191 personal_sign style.**
   `keccak256("\x19FutureChain Signed Delegation:\n" + len + json_canonical(payload))`.
   Pros: familiar pattern for anyone from Ethereum-world. Cons: ad-hoc
   for our chain.

2. **EIP-712 typed structured data.** Define a domain separator
   (`name: "FutureChain Delegation"`, `version: "1"`, `chainId`,
   `verifyingContract: backend-pubkey`) and a `SettlementDelegation`
   type. Sign the resulting `keccak256(0x1901 || domainHash || structHash)`.
   Pros: tooling exists; wallets show field-by-field preview. Cons:
   FutureChain isn't EVM-flavoured; nothing in the rest of the stack
   uses EIP-712.

3. **PACS.008-as-envelope.** Wrap the delegation in a self-referential
   PACS.008 transaction with zero amount, signed and submitted to the
   chain. The chain records the delegation. Pros: same signing flow as
   real transactions; on-chain revocation is just submitting a new
   delegation with later `validUntil`. Cons: pollutes the chain with
   delegations; adds tx fee to onboarding; conflates two concerns.

4. **Custom domain-separated SHA-256.**
   `sha256("anton-business:settlement-delegation:v1\n" + canonical_json(payload))`,
   signed with secp256k1. Simplest. Lives outside ISO 20022 entirely.

## Recommendation

**Option 4 (custom domain-separated).** Pros:
- Cleanly separates operational signatures (delegations, refunds, settings)
  from transaction signatures (PACS.008 submissions).
- No on-chain footprint until the delegation is actually used.
- Versioned via the domain string, so we can evolve without breaking.
- Trivial to implement in both TS (`@noble/hashes`) and Rust
  (`sha2` crate + `secp256k1` crate).

Drawback: no off-the-shelf wallet preview tooling. Mitigation: the app
itself renders the delegation in a human-readable form before signing.

## Required deliverables

- Envelope spec in this ADR (canonical JSON rules: key ordering, BigInt
  encoding, no trailing whitespace).
- TS implementation in `packages/futurechain-sdk/src/delegation/`.
- Rust implementation in `apps/merchant-backend/src/services/delegation.rs`.
- **Parity test fixtures** in `tests/fixtures/delegation-envelope.json`:
  10+ payloads with their expected hashes and signatures, generated by
  TS, verified by Rust (and vice versa).

## What this blocks

- Settlement orchestration in `merchant-backend`.
- Onboarding screen "Authorise auto-convert" in the app.
- ADR-002's claim of secp256k1 verification on the backend.
